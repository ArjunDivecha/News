## Assessment

This is a mature, genuinely well-built system — the strongest kind of "boring":
pure-function analytics, fail-loud discipline, and real test coverage. Do not
rewrite it. The risk is not in the math; it is in the **unattended run's silent
degradation surface**.

What is done right (evidence):
- **Financial math is pure and tested.** All formulas live in `analytics.py` as
  functions over DataFrames; contributions use beginning-of-day weights so they
  tie exactly to dollar P&L (`analytics.py:396-412`), shorts sign automatically,
  and YTD is renormalized by measured weight so missing-YTD names don't dilute
  toward zero (`analytics.py:413-418`, `:645-651`). 105 tests pass in ~1.5s.
- **Fail-loud where it counts.** SPY-absent raises rather than emitting a
  benchmark-less report (`analytics.py:187-190`); coverage <90% raises
  `DataCoverageError` (`data.py:252-255`); a `max_tokens` stop raises
  `ReportTruncatedError` and is deliberately non-retryable (`llm.py:60-67`,
  `:138-141`, `:220-226`).
- **The two worst historical bugs are fixed at the root, not papered over.**
  Holiday rows are dropped once, upstream of all analytics
  (`data.py:159-181` + `main.py:146`); the launchd FD-exhaustion bug is fixed by
  raising `RLIMIT_NOFILE` before the threaded download (`data.py:74-99`).
- **STALE > n/a is implemented consistently** (last-available carry-forward in
  `analytics.py:90-99`, `:356-361`, `:514-524`), honoring the project NO-`n/a` rule.

Where the real risk is (evidence):
1. **Additive sections fail into a stderr void.** Tag views, allocation +
   scenarios, and the policy check are each wrapped in a bare
   `except Exception` that prints a traceback and continues
   (`main.py:223-227`, `:257-262`, `:285-289`). Intent (never sink the daily
   report) is right, but the catch is too wide: a `KeyError` from a future
   refactor ships a report **missing whole sections** with only a traceback in
   `daily_run.log` that nobody reads. There is no signal to the reader that the
   report they got is degraded.
2. **The LLM backend degrades silently and now costs money.** When the Claude
   CLI is not on PATH, `generate_report` falls back to the metered API
   (`llm.py:286-295`) and `run_daily.sh` merely logs `Claude CLI: NOT FOUND`;
   Fable's Desk (CLI-only) is skipped with no alert. This actually happened on
   the 2026-07-06 launchd run. With Fable moving to API pricing on 2026-07-07,
   that silent fallback is a live cost exposure, not just a quality one.
3. **No holistic guard on the assembled package, and the three household totals
   are never reconciled.** `tests/test_report_pipeline.py:228-231` checks
   no-`n/a` for exactly one synthetic scenario; there is no golden fixture that
   assembles the whole package over the known-hard inputs at once, and
   `compute_subportfolios` TOTAL, `compute_asset_allocation`, and the combined
   `compute_portfolio` are never asserted to agree. This is the P0.

Minor smells (low urgency): `_load_gmo()` is read twice per run
(`main.py:126` and `:183`); `aggregate_holdings` uses `groupby().apply()`
(`analytics.py:322`), fragile across pandas versions; a user-supplied
`--date` landing on a holiday is not validated against real trading dates
(`main.py:147`); `main.py:34` docstring still says "Claude Opus" though the
writer is Fable; `report/README.md:88,:91` say "35"/"25 tests" (actual 105).

## Prioritized improvements

### P0 — Report-health golden gate over an adversarial fixture
- **What & why:** One deterministic gate that assembles the full data package
  from a frozen fixture carrying every known-hard case (holiday row, stale fund,
  short, unpriced sleeve) and asserts it is clean and self-consistent. The git
  history is a string of distinct silent-degradation incidents; today each new
  one ships before it is caught. Evidence: `main.py:146`, `data.py:159-181`,
  `analytics.py:187-190`, `tests/test_report_pipeline.py:228-231`.
- **Bet:** *if* the non-LLM pipeline runs on the adversarial fixture, *then* the
  package has no literal `n/a`, benchmark legs present, every table row matches
  its header width, and the three household totals reconcile within tolerance;
  *observable:* one gate exits 0, and exits nonzero naming the check when any
  condition is broken.
- **Invariants:** INV1 no-`n/a`; INV2 SPY+ACWI+TLT present; INV3 table
  row-width == header-width; INV4 household totals agree within tolerance.
- **Gate intents:** `pytest tests/test_report_health.py` proves INV1-4 on the
  fixture; full suite stays green.
- **Effort:** ~half a day (fixture builder is the bulk).
- Full contract below.

### P1 — Silent-degradation observability (run manifest + DEGRADED flag)
- **What & why:** Emit a per-run manifest recording the facts that currently
  vanish into the log: which LLM backend actually served the report
  (subscription CLI vs metered API), whether Fable's Desk ran, which additive
  sections were SKIPPED, price coverage %, and holdings staleness. Surface a
  `DEGRADED` marker in the emailed report's subject/first line when any of these
  is off-nominal. Evidence: `llm.py:286-295`, `main.py:223-289`,
  `run_daily.sh` (`Claude CLI: NOT FOUND`).
- **Bet:** *if* a run degrades (metered fallback fired, Desk skipped, a section
  SKIPPED, coverage below a threshold, or holdings stale), *then* the manifest
  records each condition and the email subject is prefixed `DEGRADED`;
  *observable:* a unit test feeding each degraded signal asserts the manifest
  flags it and the subject changes; a clean run produces no `DEGRADED`.
- **Invariants:** every degradation condition maps to exactly one manifest flag;
  a fully-clean run sets zero flags and no `DEGRADED` prefix.
- **Gate intents:** `pytest` over a manifest-builder unit test with clean and
  degraded inputs; assert exit-0 and the expected flag set for each.
- **Effort:** ~half a day.

### P1 — Narrow the additive-section exception handling
- **What & why:** Replace the three bare `except Exception` blocks
  (`main.py:223-227`, `:257-262`, `:285-289`) so they record the skip into the
  P1 manifest and re-raise on programming errors that are not legitimately
  data-driven, rather than swallowing everything.
- **Bet:** *if* an additive section raises a genuine data-shape error, *then* it
  is recorded as a SKIPPED flag in the manifest (report still ships); *if* it
  raises an unexpected type, *then* the run fails loud; *observable:* tests that
  inject each case assert the correct branch.
- **Invariants:** a SKIPPED section never silently disappears from the reader's
  view without a manifest flag.
- **Gate intents:** `pytest` unit tests injecting a data error vs a code error.
- **Effort:** ~2 hours (depends on P1 manifest).

### P2 — Doc & drift cleanup
- **What & why:** Fix stale test counts (`report/README.md:88,:91` → 105),
  the "Claude Opus" docstring (`main.py:34` → Fable 5), and the duplicate
  `_load_gmo()` read (`main.py:126` and `:183`).
- **Bet:** *if* a reader greps the docs for the test count or model, *then* they
  match reality; *observable:* `grep -c` matches; the duplicate call is gone.
- **Invariants:** no doc line states a test count or writer model that the code
  contradicts.
- **Gate intents:** a doc-lint test asserting the README's stated test count
  equals the collected count from `pytest --collect-only`.
- **Effort:** <1 hour.

### P2 — Validate `--date` against real trading days
- **What & why:** A user-supplied `--date` on a US holiday is not checked
  against the sparse-row-filtered index (`main.py:147`), so analytics could
  anchor to a dropped row.
- **Bet:** *if* `--date` is not a real trading date in the filtered matrix,
  *then* the run fails loud (or snaps to the prior real session with a printed
  notice); *observable:* a test passing a holiday date asserts the guard fires.
- **Invariants:** analytics never anchor to a date absent from the filtered matrix.
- **Gate intents:** `pytest` with a holiday `--date` argument.
- **Effort:** ~1 hour.

## Context

This contract adds a deterministic health gate for the unified daily report in
`/Users/arjundivecha/Dropbox/AAA Backup/A Working/News`. The production path is
`report/main.py`; before the LLM is ever called it assembles a Markdown "data
package" (via `report/prompt.py` build_data_package) that is exactly what the
model sees and is archived to `outputs/unified/Data_Package_<date>.md`. If that
package is malformed, the report inherits the defect.

The git history of this repo is a sequence of silent-degradation incidents in
this package: 2026-06-18 the report truncated mid-table; 2026-06-22 it came out
~84 percent "n/a" because a Juneteenth holiday row poisoned pct_change; the
07-01 through 07-04 launchd runs under-covered prices. Each was a distinct new
failure mode caught only after a bad report shipped. The existing suite
(`tests/`, 105 tests, all passing as of 2026-07-06) checks these piecemeal — for
example `tests/test_report_pipeline.py` asserts no "n/a" for one synthetic
scenario — but there is no single golden-fixture gate that assembles the whole
package over the known-hard cases at once, and the three household-total
computations (compute_subportfolios TOTAL, tag_analytics.compute_asset_allocation,
and the combined compute_portfolio) are never asserted to reconcile.

Definitions. "Data package" is the string returned by
`report/prompt.py` build_data_package. "Adversarial fixture" is a small frozen
price and holdings dataset built inside the test that contains, together: a
sparse US-holiday date row (the filter_sparse_rows case), a fund whose last real
print predates the as-of date (the STALE case), a short position (negative
market value), and an unpriced manual sleeve (the em-dash genuinely-undefined
case). "Household total" is total portfolio value including cash, off-broker
sleeves, and GMO. The gate must build its own fixture and must never read or
mutate the live `data/report.db`. This section is stateless: an agent with no
memory of this repo can read the files named above plus `report/README.md` and
`openwiki/quickstart.md` to orient, then implement against the real code.

## Build Loop vs Product Loop

Build loop (machine-provable now): a new test builds the adversarial fixture,
calls the real analytics and build_data_package, and asserts the four
invariants. Gate G1 is that test; it must exit nonzero and name the failing
check when any invariant is broken (drop SPY, leave the holiday row unfiltered,
corrupt a table, or perturb one household total past tolerance). Gate G2 keeps
the existing 105-test suite green so the fixture and any prompt.py hook did not
regress live behavior. Passing both gates proves the assembled package is
structurally clean and self-consistent on the known-hard inputs.

Product loop (only measurable in production): the real bet is fewer
silent-degradation incidents in unattended launchd runs — no more shipped
reports that are mostly "n/a", truncated, or internally inconsistent. That can
only be confirmed by watching live daily runs over weeks. The coding model
may not claim the product bet is satisfied merely because the gates pass: a
green gate proves the fixture cases are covered, not that every future
real-world degradation mode is caught. New live failure modes should be added
as fixture rows and re-gated.
